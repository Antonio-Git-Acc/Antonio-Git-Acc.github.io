# Algorithms and Data Structures Enhancement

**Artifact:** Grazioso Salvare Dashboard
**Original course:** CS 340 – Advanced Programming Concepts

The artifact I selected for the Algorithms and Data Structures category is the Grazioso Salvare Dashboard, originally created in CS 340: Advanced Programming Concepts. It is a full-stack Python application that connects to a MongoDB database containing the Austin Animal Center Outcomes dataset and provides an interactive dashboard for identifying rescue dog candidates. The application consists of a reusable CRUD module (CRUD_Python_Module.py) that encapsulates all database interactions through an AnimalShelter class, and a Jupyter notebook (ProjectTwoDashboard.ipynb) built with Dash, Plotly, and Dash Leaflet that presents a filterable data table, a breed-distribution pie chart, and a geolocation map.

The original implementation worked correctly but was not optimized. Queries performed full collection scans, the entire collection was loaded into memory at startup, breed counts were computed in Python rather than on the database server, and rescue-type parameters were duplicated as hardcoded values in multiple places.
	I selected this artifact because it demonstrates applied algorithms and data structures in a realistic data-intensive context. The components that showcase my skills include:
1.	Query optimization through indexing. The rescue-type queries filter on breed, sex_upon_outcome, and age_upon_outcome_in_weeks. I added a compound index matching that field order so MongoDB can satisfy the query with a single index scan rather than a full collection scan, reducing lookup complexity from O(n) to O(log n). I also added a geospatial index (2dsphere) on the location field.
2.	Paginated reads. The original read() method returned every matching document as a Python list, giving O(n) memory usage. The enhanced version accepts page and page_size parameters and uses skip() and limit(), reducing memory from O(n) to O(k), where k is the page size.
3.	Server-side aggregation. The pie chart previously loaded all matching documents into Python and called value_counts()—an O(n) operation on the client. The enhanced version uses MongoDB's aggregation pipeline ($match, $group, $sort) so the counting happens on the server and only the aggregated results cross the network.
4.	TTL query cache. I implemented a time-to-live cache keyed on a hashable serialization of the query, page, and page size. Repeated filter selections resolve in O(1) instead of re-issuing a database query. The cache is invalidated automatically on any create, update, or delete operation.
5.	Hash-map row lookup. The map callback originally used dff.iloc[row], which depends on DataFrame ordering. The enhanced version builds a dictionary keyed by animal_id, giving O(1) lookup that is robust to sorting and filtering.
6.	Centralized configuration. The duplicated breed and age-range values in build_query() were extracted into a rescue_config.py module, eliminating magic values and making the rescue categories data-driven and easily extensible.
7.	Data normalization pipeline. Because the original CS 340 dataset was stored on a Jupyter instance that is no longer accessible, I wrote a transformation script (transform_data.py) that converts the raw Austin Animal Center CSV schema (space-separated column names, text-formatted ages) into the snake_case numeric schema the code expects. This includes computing age_upon_outcome_in_weeks from text values like "1 year" and adding synthetic location coordinates so the map widget has data to display.
8.	Input validation and resource cleanup. All public CRUD methods now validate their inputs, and a close() method was added so the MongoDB connection is released cleanly.
The warm/cold cache comparison shows a roughly 10× speedup on repeated identical queries, which confirms the O(1) behavior the cache is designed to provide. The count() and aggregation results confirm that returning summary data instead of full documents keeps response times under one millisecond even on a collection with tens of thousands of records.
This enhancement directly addresses Course Outcome 3 (Design and evaluate computing solutions using algorithmic principles and managing trade-offs) by demonstrating and justifying complexity improvements—O(n) to O(log n) for lookups, O(n) to O(k) for memory, and O(n) to O(1) for cached queries. It also supports Course Outcome 4 (Use well-founded techniques and tools) through the correct application of MongoDB indexing, aggregation pipelines, and caching patterns. It partially addresses Course Outcome 5 (Security mindset) by replacing hardcoded credentials with environment variables, though the deeper security work belongs to the Databases enhancement.
I have no updates to my outcome-coverage plan. The enhancement aligns with what I proposed in Module One, with one honest addition: the data normalization step was not in the original plan but became necessary when the original dataset proved inaccessible. Documenting and solving that problem was itself valuable—it demonstrated that real enhancements rarely go exactly as planned, and that adapting to constraints while preserving the original design intent is part of professional practice.
The most valuable lesson from this enhancement was learning to think about where computation happens. In the original code, all the logic lived in Python on the client side—loading documents, counting breeds, filtering rows. Every one of those operations had a cost that scaled with the size of the dataset. The enhanced version moves as much work as possible to the database, where indexes and aggregation pipelines can operate far more efficiently than equivalent Python code. This is a fundamentally different way of thinking about application design than what I had practiced before.
The biggest technical challenge was the caching layer. My first attempt used functools.lru_cache, but the query dictionaries are not hashable, so the decorator failed immediately. I then wrote a manual cache, only to discover that the rescue queries themselves contain nested dictionaries (like {'$in': [...]} and {'$gte': 26, '$lte': 156}), which also aren't hashable. I resolved this by serializing each query to a stable JSON string with json.dumps(query, sort_keys=True) and using that string as the cache key. This forced me to think carefully about cache invalidation as well—when a user inserts, updates, or deletes a record, the cache must be cleared or the dashboard will display outdated results. I clear the cache inside each write method.
The second challenge was a trade-off decision around pagination. The read() method now supports pagination, but the Dash DataTable has its own client-side pagination, so wiring the two together cleanly would have required rewriting the sorting and filtering callbacks. I chose to bound the initial read at a configurable maximum row count and document full server-side pagination as future work. This is an honest trade-off, and articulating it has strengthened my understanding of when to stop optimizing.
The third challenge was environmental rather than algorithmic. The original CS 340 notebook was hosted on a Jupyter instance I no longer have access to, so I had to re-import the raw Austin Animal Center CSV from the public data portal and write a transformation script to bring it into the schema my code expected. That transformation also had to compute numeric age-in-weeks from text and generate synthetic coordinates since the raw dataset contains no location fields. This step was unplanned but instructive—it demonstrated that real data work often involves as much cleaning and normalization as it does query logic.
