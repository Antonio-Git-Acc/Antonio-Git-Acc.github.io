# Databases Enhancement

**Artifact:** EventTracker Android Application
**Original course:** CS 360 – Mobile Architecture and Programming

The artifact I selected for the Databases category is the EventTracker Android application, originally created in CS 360: Mobile Architecture and Programming. It is a native Android app that allows users to create, view, and delete events, with support for local notifications and optional SMS reminders. The application uses Google's Room persistence library, an abstraction over SQLite, to store data locally on the device. The original implementation consisted of just two tables — users and events — with minimal relationships, no indexes on queried columns, a static salt for password hashing, and a destructive migration strategy that discarded all user data whenever the schema changed. Functionally it worked, but it did not reflect production-grade database design or security practices.

I selected this artifact because it provided a realistic and focused opportunity to demonstrate database design, security, and migration skills. The enhancements I made address both functional and non-functional requirements and were validated empirically through targeted tests. I expanded the database from two tables to five: users, events, categories, recurring_events, and notification_history. The new tables support event categorization and recurring event scheduling, and they demonstrate my ability to design a normalized relational schema that supports richer application features. I added foreign key constraints from events to users (with ON DELETE CASCADE) and from events to categories (with ON DELETE SET NULL), plus additional foreign keys from recurring_events and notification_history to events (both ON DELETE CASCADE). I verified cascade behavior empirically: after inserting an event with a dependent notification history row and then deleting the event, the dependent row was removed automatically (Cascade worked: true in the verification log). I added indexes on the columns used by the most frequent queries: user_id, category_id, and a composite index on event_date and event_time. Room's generated SQL now uses these indexes for ordered lookups, replacing full table scans. I implemented JOIN and aggregate queries that go beyond basic CRUD: a LEFT JOIN that returns events with their category name and color, and a GROUP BY aggregate that counts events per category. Both were exercised successfully against the live database. The original code hashed passwords with a static salt string ("staticSalt"), which is vulnerable to rainbow-table attacks and produces identical hashes for identical passwords across users. I replaced this with a randomly generated, per-user salt stored alongside the password hash. The fix was verified by hashing the same password with two different salts and confirming that the resulting hashes differ. I integrated SQLCipher to encrypt the entire Room database file. The passphrase is a randomly generated 256-bit value created on first run and stored securely via the Android Keystore, encrypted with an AES-256-GCM key. Encryption was verified by exporting the database file from the device and attempting to open it in a standard SQLite viewer; the file is rejected as "not a database," confirming that the contents are encrypted. I replaced fallbackToDestructiveMigration() with explicit Migration objects that transition the schema from version 1 to version 3 without data loss. The migrations create the new tables, add the new columns, and establish the foreign key relationships. I acknowledge one limitation in the narrative below. Removing allowMainThreadQueries() — which is required for a production-grade app — surfaced a latent threading bug: LoginViewModel was calling synchronous DAO methods directly from the UI thread. I fixed this by moving database work to the shared background executor and exposing results via LiveData. This is a standard Android pattern for database-backed UI and is documented below as a reflection point.

This enhancement met more outcomes than I originally planned. It directly supports Course Outcome 3 (Design and evaluate computing solutions) through the normalized schema, foreign key design, and query optimization. It supports Course Outcome 4 (Use well-founded techniques and tools) through SQLCipher, the Android Keystore, and Room's migration API. Most importantly, it strongly demonstrates Course Outcome 5 (Develop a security mindset): I identified two separate security weaknesses (static salt, unencrypted database), designed mitigations, and verified them empirically. I have one honest update to my outcome-coverage plan: the migration code is defined but not exercised in practice, because the original database was unencrypted and SQLCipher cannot open an unencrypted database. A production deployment would require a one-time conversion step using SQLCipherUtils.encryptTo() to convert the plaintext database into an encrypted one. I have documented this as future work rather than pretending the migrations were tested.

This enhancement taught me more about real-world database engineering than any of the previous milestones, for three reasons. First, I learned that security is layered. Fixing the static salt was straightforward once identified — but a salted hash still lives inside an unencrypted file. Encrypting the database meant the hashes themselves became protected at rest, and encrypting the passphrase with an Android Keystore key meant the encryption key itself was protected by hardware-backed storage. Each layer depends on the one below it, and no single fix would have been sufficient. Second, I learned that enhancements surface latent bugs. When I removed allowMainThreadQueries(), the app crashed the moment any user tried to log in, because the ViewModel was calling synchronous DAO methods directly from the UI thread. The original code had this bug for its entire life — it simply never manifested because allowMainThreadQueries() disabled Room's safety check. Fixing it meant restructuring LoginViewModel to run work on a background executor and expose results via LiveData, which is the correct pattern regardless of whether an app is encrypted. Third, I learned that migration code must be honest. It is tempting to write migration objects, see that the app builds and runs, and assume migrations work. But my migration code has never actually run in practice, because SQLCipher cannot open the unencrypted database the migration would have started from. This is a real limitation that I have chosen to document rather than obscure. Real production migrations would need to be tested against a copy of the previous database file, and this is exactly the kind of gap that a security-conscious engineer must be willing to admit.
The most challenging parts were the SQLCipher integration (particularly the secure passphrase management) and the migration path. The SQLCipher work required understanding the Android Keystore API, the correct use of AES-GCM with associated IVs, and the interaction between the encrypted factory and Room's builder. The threading fix required understanding the Android lifecycle and threading model. Both were instructive and have made me a more careful engineer.
